# 支付与充值流程说明

## 1. 目标

本文件定义 `web` 产品线在匿名会话前提下的支付与充值流程，用于支撑“先付费，再处理”的商用闭环。

一期目标：

- 支持匿名会话
- 支持充值或单次支付
- 支付成功后才能启动 OCR 任务
- 保证支付回调与扣费操作幂等

## 2. 商业规则

### 2.1 支付原则

- 未支付任务不得进入 OCR 队列
- 优先支持“充值余额 + 按次扣费”
- 若余额不足，则先引导充值或付款

### 2.2 扣费时点

推荐固定为：

1. 用户创建任务
2. 系统校验余额或支付状态
3. 在任务真正进入 `queued` 前完成扣费锁定
4. 扣费成功才启动 OCR

### 2.3 失败补偿

- OCR 任务失败：保留失败记录并进入补偿判断
- Word 渲染失败：保留失败记录并进入补偿判断
- 补偿方式可为：
  - 原路退回余额
  - 标记人工处理
  - 发放一次补处理资格

一期建议默认：

- 统一退回余额
- 不做复杂人工工单流

## 3. 匿名会话下的钱包模型

由于一期不做正式登录，充值与余额依附于匿名会话：

- `anonymous_session_id`
- `wallet_balance`
- `wallet_status`

约束：

- 钱包余额只对当前匿名会话有效
- 会话过期后，余额保留策略需单独定义

一期建议：

- 匿名会话有效期内保留余额
- 超过有效期后，可进入“待认领”或“清理前人工保留”策略
- 该策略后续可在手机号登录后收敛到账户体系

## 4. 支付主流程

### 4.1 充值流程

1. 用户进入充值页
2. 后端创建充值订单
3. 页面展示二维码
4. 支付平台回调
5. 系统确认到账并增加余额
6. 前端刷新钱包状态

### 4.2 任务支付流程

1. 用户创建任务
2. 系统判断余额是否充足
3. 若足够，直接冻结/扣减余额
4. 若不足，跳转充值或付款
5. 扣费成功后，任务进入 `queued`

## 5. 订单状态机

建议订单状态：

- `created`
- `pending_payment`
- `paid`
- `credited`
- `failed`
- `expired`
- `refunded`

说明：

- `paid`：支付平台已确认付款
- `credited`：余额已入账或任务扣费已生效

## 6. 幂等规则

以下动作必须幂等：

- 充值订单创建
- 支付回调
- 余额入账
- 任务扣费
- 失败退款/返还余额

推荐字段：

- `idempotency_key`
- `payment_provider_txn_id`
- `credit_ledger_id`

## 7. 关键接口

推荐接口：

- `POST /payments/orders`
- `POST /payments/topups`
- `POST /payments/callback`
- `GET /wallet`
- `POST /tasks`

### 7.1 `POST /tasks` 的扣费行为

必须明确：

- 创建任务时不能直接默认进入 OCR
- 必须先完成：
  - 会话校验
  - 余额或支付状态校验
  - 扣费/冻结成功

然后才能推进到 `queued`

## 8. 风险点

- 匿名会话失效导致用户余额归属不清
- 支付回调重复投递导致重复入账
- OCR 失败但余额未返还
- 扣费成功但任务未创建

## 9. 最小实施步骤

1. 建立充值订单模型
2. 建立钱包余额与流水模型
3. 接入二维码支付与回调
4. 在任务创建前增加余额校验与扣费锁定
5. 建立失败返还余额逻辑
6. 为后续手机号登录预留余额绑定迁移能力
